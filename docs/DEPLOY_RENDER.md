# Deploying AnaRisk to Render (backend) + Vercel (frontend)

This guide covers the production deployment that this repository is configured for:
the FastAPI backend and PostgreSQL on **Render**, the React dashboard on **Vercel**.

The repository ships a validated Render Blueprint ([render.yaml](../render.yaml)) that
creates both resources with migrations and a real readiness check wired in.

---

## Why the readiness check matters (the "deploy succeeded, login 500" incident)

Render originally reported a successful deploy because it only checked that the process
was alive. The liveness endpoint (`/api/v1/health`) intentionally never touches the
database, so a broken `DATABASE_URL` still produced a green deploy while **every
DB-backed request — including login — returned HTTP 500**.

The root cause was the URL shape providers hand out: `postgres://…`. That scheme is not
loadable by SQLAlchemy 2 + psycopg 3, so engine creation failed with
`NoSuchModuleError: Can't load plugin: sqlalchemy.dialects:postgres` on the first query.

Three layers now prevent a repeat:

1. **Automatic URL normalisation** (`backend/app/db/url.py`): every legacy scheme
   (`postgres://`, `postgresql://`, `postgresql+psycopg2://`) is rewritten to
   `postgresql+psycopg://` at settings-load time, `alembic` runtime, and the test
   harness. Credentials/host are never modified; an explicit `sslmode` is respected,
   and `sslmode=require` is added automatically for `*.render.com` hosts.
2. **A startup database probe** (`backend/app/main.py`): at boot the app verifies the
   database is reachable AND migrated, and logs an actionable error otherwise. The
   process stays up so the problem is visible in logs and `/api/v1/ready`.
3. **A real readiness endpoint**: `/api/v1/ready` checks connectivity + migration
   revision and returns **503 (not 500)** with a JSON body when the database is down.
   The Render Blueprint uses it as `healthCheckPath`, so a broken deploy is marked
   *failed* instead of "green but every request 500s".

## Deploy with the Blueprint (recommended)

1. Push this repository to GitHub.
2. In the Render Dashboard: **New → Blueprint** and select the repository.
   Render reads [render.yaml](../render.yaml) and creates:
   - `anarisk-db` — managed PostgreSQL (free plan; upgrade for production)
   - `anarisk-api` — the FastAPI web service (`rootDir: backend`)
3. At the first sync Render prompts for the variables marked `sync: false`
   (see the table below). Fill them in.
4. Watch the deploy log. You must see:
   - `preDeployCommand` → `alembic upgrade head` completing
   - `database probe ok (migration revision 0005)` from the app
   - the health check passing on `/api/v1/ready`

### Build / start / migration commands (already in the Blueprint)

| Phase | Command |
|---|---|
| Build | `pip install -r requirements.txt` |
| Pre-deploy (migrations) | `alembic upgrade head` |
| Start | `uvicorn app.main:app --host 0.0.0.0 --port $PORT` |
| Health check | `GET /api/v1/ready` |

## Environment variables

`DATABASE_URL` is rendered automatically from the `anarisk-db` connection string.
`SECRET_KEY` is generated once by Render. Everything else you set in the dashboard.

| Variable | Value | Notes |
|---|---|---|
| `ENVIRONMENT` | `production` | Disables `dev_otp`/`dev_reset_token` in responses; enables the seed guard |
| `DEBUG` | `false` | |
| `SECRET_KEY` | *(generated by Render)* | Never commit a real value |
| `DATABASE_URL` | *(from `anarisk-db`)* | Either shape works now; the app normalises it |
| `CORS_ORIGINS` | `https://your-project.vercel.app` | Comma-separated. **Must match the Vercel origin exactly** or the browser blocks login calls |
| `FRONTEND_URL` | `https://your-project.vercel.app` | Base URL for password-reset links |
| `EMAIL_PROVIDER` | `smtp` (or `resend`) | See [EMAIL_SETUP.md](EMAIL_SETUP.md) |
| `SMTP_HOST` | e.g. `smtp.gmail.com` | |
| `SMTP_PORT` | `587` | |
| `SMTP_STARTTLS` | `true` | |
| `SMTP_USERNAME` | *(secret)* | |
| `SMTP_PASSWORD` | *(secret)* | For Gmail: app password, never the account password |
| `EMAIL_FROM_ADDRESS` | *(secret)* | Must be a verified sender |
| `EMAIL_FROM_NAME` | `AnaRisk` | |
| `AI_PROVIDER` | `none` / `openai-compatible` | If `openai-compatible`, also set `AI_BASE_URL`, `AI_API_KEY`, `AI_MODEL` |
| `MONITORING_WORKER_ENABLED` | `true` | Keep `false` on extra instances to avoid duplicate schedulers |
| `MONITORING_INTERVAL_SECONDS` | `300` | |
| `RATE_LIMIT_ENABLED` | `true` | Client IPs come from `X-Forwarded-For` (last entry), so limits are per-user behind Render's proxy |
| `ALLOW_PUBLIC_REGISTRATION` | `true` | First account self-registers through the UI |

### Vercel side

Set exactly one variable in the Vercel project (**Settings → Environment Variables**):

| Variable | Value |
|---|---|
| `VITE_API_BASE_URL` | `https://your-api.onrender.com` (origin only — the app appends `/api/v1` itself) |

Then redeploy the frontend so the build picks it up. There are **no secrets** on the
frontend; never put API keys or SMTP credentials in `VITE_*` variables — they are
embedded into the public JS bundle.

## Post-deploy verification checklist

Run these from any machine; they require no credentials:

```bash
API=https://your-api.onrender.com

curl -s $API/api/v1/health   # {"status":"ok",...}
curl -si $API/api/v1/ready   # HTTP/1.1 200 {"status":"ready","database":"ok","migration_revision":"0005"}
```

Then, with the frontend deployed:

1. Open the Vercel URL → the login page loads (no CORS errors in the browser console).
2. Register a new account → you get `email_sent: true` and the OTP arrives
   (with `ENVIRONMENT=production` the response never contains `dev_otp`).
3. Verify the email with the 6-digit code, then log in → **HTTP 200 with a token**.
4. Wrong password **and** unverified email → HTTP 401 `invalid_credentials` (uniform — the
   login screen never reveals whether an account exists; unverified users sign up again to
   get a fresh code). Neither is a 500.
5. In Render's logs you should see `database probe ok (migration revision 0005)` —
   and **no** `DATABASE PROBE FAILED` / `MIGRATIONS NOT APPLIED` lines.

If `/ready` reports 503, the body tells you which of the two cases you are in:

- `unreachable or not migrated` → check `DATABASE_URL`, credentials, network, TLS
- `schema out of date` → run `alembic upgrade head` (the Blueprint runs it on every
  deploy via `preDeployCommand`, so this indicates a manual/older setup)

## Common failures and what they mean

| Symptom | Cause | Fix |
|---|---|---|
| Deploy green, login 500 | Old builds only; a DB error at query time | Update to this build; `/ready` now fails the deploy honestly |
| CORS error in browser, API works in curl | `CORS_ORIGINS` doesn't match the Vercel origin exactly (trailing slash, `http` vs `https`) | Set the exact origin, redeploy |
| Signup returns `email_sent: false` / `delivery_failed` | SMTP/Resend misconfigured | See [EMAIL_SETUP.md](EMAIL_SETUP.md); check Render logs for the delivery error |
| Password reset returns 503 | `EMAIL_PROVIDER=none` in production | Configure SMTP or Resend |
| Login 429 for every user at once | Not possible with this build (per-IP buckets); if seen, `trust_proxy_headers` disabled | Leave `TRUST_PROXY_HEADERS` unset (default on) |
| Uploaded evidence disappears on redeploy | Free plan has no persistent disk | Attach a Render disk and set `UPLOAD_DIR` (commented block in `render.yaml`) |

## Notes on the free plan

- The free Postgres (0.1 CPU / 256 MB) and free web instance (spins down when idle)
  are fine for a demo. First request after idle takes ~30s while the instance wakes.
- The app adds `sslmode=require` for `*.render.com` hosts automatically.
- Production workloads: upgrade the instance and database plan, attach a disk for
  `UPLOAD_DIR`, and run more than one instance only with `MONITORING_WORKER_ENABLED=true`
  on exactly one of them (scheduler claims are `FOR UPDATE SKIP LOCKED`, but keeping a
  single scheduler avoids duplicate notification runs).
